# 02-user-config: one registry profile in every client's user config

`user-config` renders a profile from `config/registry.profiles.json` into the user-level config file of each JavaScript client, so a plain `npm install`, `pnpm install`, `bun install`, `yarn` or `vlt install` uses the same registry without any project files. It shows the pending change as a unified diff, applies it with timestamped backups and atomic writes, reports which files it manages, and restores the previous state one step at a time.

The three entrypoints (`user-config.sh`, `user-config.nu`, `user-config.ts`) take the same flags and produce byte-identical files; `test.sh` checks that.

## Targets

| Target | File written | Read by |
|---|---|---|
| `npmrc` | `$HOME/.npmrc` | npm, pnpm, yarn classic, bun (when no bunfig sets a registry), deno |
| `bunfig` | `$XDG_CONFIG_HOME/.bunfig.toml` when `XDG_CONFIG_HOME` is set, else `$HOME/.bunfig.toml` | bun |
| `yarnrc` | `$HOME/.yarnrc.yml` | yarn berry (2+) |
| `vlt-json` | `${XDG_CONFIG_HOME:-$HOME/.config}/vlt/vlt.json` (merged) | vlt |
| `env` | `${XDG_CONFIG_HOME:-$HOME/.config}/vlt-lab/env.sh` and `env.nu` | your shell, once sourced |

Every file except `vlt.json` starts with `# generated by vlt-lab from profile NAME; do not edit`, which is how `status` recognises it. `vlt.json` has no comment syntax, so `user-config` merges instead of overwriting: it owns `config.registries`, `config.scoped-registries` and `config.command.build`, and keeps every other key (for example `config.identity` or `config.command.install`) in place. vlt only reads options nested under `"config"` (see `docs/research/vlt-1.3.6-facts.md`, section 1).

The bunfig location follows bun's own lookup, which this example measured (see Results): with `XDG_CONFIG_HOME` set, bun 1.4.2 ignores `$HOME/.bunfig.toml`.

## Per-client precedence notes

- **npm 10.9**: `npm_config_*` environment variables beat `$HOME/.npmrc`, and `NPM_CONFIG_USERCONFIG` (or `npm_config_userconfig`) replaces `$HOME/.npmrc` entirely. The machine this was built on exports `NPM_CONFIG_USERCONFIG=/root/.npmrc`, so `$HOME/.npmrc` is never read there unless that variable is cleared. `status` and `apply` print a note when it points elsewhere.
- **pnpm 10.28**: reads the same `$HOME/.npmrc`. The vlt docs report that pnpm 11.5.3 and later ignore `${VAR}` placeholders in a project `.npmrc` (vlt, 2026); user-level registry lines are unaffected, and pnpm 10.28 expanded `${VSR_TOKEN}` from a user-level npmrc (passed through `npm_config_userconfig`) in the token test of example 03.
- **bun 1.4.2**: `bunfig.toml` wins over `.npmrc` when both set a registry (observed here; the vlt docs say this holds only on bun 1.4 and newer (vlt, 2026)). The global bunfig is `$XDG_CONFIG_HOME/.bunfig.toml` when `XDG_CONFIG_HOME` is set, and `$HOME/.bunfig.toml` otherwise. In bunfig only the unbraced `$VLT_TOKEN` form expands (vlt, 2026); the renderer emits that form, and bun sent the expanded `$VSR_TOKEN` to a test registry here.
- **yarn classic 1.22**: reads `$HOME/.npmrc` for `registry=` and auth lines, but sends `_authToken` only with `always-auth=true` (see example 03).
- **yarn berry**: ignores `.npmrc` completely and reads `$HOME/.yarnrc.yml`. Berry is not installed on this machine, so the `yarnrc` target is rendered and managed but was not exercised by a real yarn berry run.
- **vlt 1.3.6**: ignores `.npmrc`; it reads `vlt.json` from the XDG config dir, then a project `vlt.json` on top. Without a `registries.npm` entry every install fails, so the user file is what makes a bare `vlt install` work.

## Usage

```sh
sh user-config.sh diff --profile npmjs                 # show what would change (default command)
sh user-config.sh apply --profile npmjs                # back up, write, print the restore command
sh user-config.sh status                               # target, state, profile, path (tab separated)
sh user-config.sh restore                              # put back the newest backup per target
VLT_ACCOUNT=acme nu user-config.nu apply --profile vlt-hosted --targets npmrc,vlt-json
bun user-config.ts apply --profile npmjs --home /tmp/somewhere   # treat DIR as HOME
```

- `--profile` defaults to `$VLT_LAB_PROFILE`, then the document default (`npmjs`).
- `--targets` takes a comma-separated subset of `npmrc,bunfig,yarnrc,vlt-json,env`.
- `--home DIR` treats DIR as `HOME` and ignores an inherited `XDG_CONFIG_HOME` (config dir becomes `DIR/.config`, bunfig goes to `DIR/.bunfig.toml`), so nothing lands outside DIR.
- `apply` skips files whose content already matches, so repeating it creates no new backups. Backups are named `<file>.vlt-lab.<UTC YYYYmmddTHHMMSSZ>.bak`; writes go to `<file>.vlt-lab.tmp.<pid>` and are renamed into place.
- `restore` moves the newest backup back over the file (consuming it, so a second `restore` steps further back). A managed file with no backup was created by `apply`, so `restore` removes it.
- `status` states: `missing`, `unmanaged`, `managed`, `drifted` (header present, content differs from a fresh render). For `vlt.json`, a file counts as managed by the first profile whose merge leaves it unchanged; profiles that need unset variables (such as `vlt-hosted` without `VLT_ACCOUNT`) cannot be matched.
- With the `env` target, apply prints how to load the variables: `. ~/.config/vlt-lab/env.sh` in sh, `source ~/.config/vlt-lab/env.nu` in Nushell.

## Results

Observed on 2026-10-04 with vlt 1.3.6, npm 10.9.4, pnpm 10.28.0, bun 1.4.2, yarn 1.22.22, Nushell 0.116.0, jq 1.7.

`sh test.sh`: **97 passed, 0 failed** in 12 s. Every run uses a fresh `mktemp` HOME with `XDG_CONFIG_HOME`, `XDG_DATA_HOME` and `XDG_CACHE_HOME` inside it, and clears `NPM_CONFIG_USERCONFIG`.

| Check | Outcome |
|---|---|
| `diff` prints a unified diff and changes no file (sh, nu, ts) | pass |
| `apply` npmjs over a seeded `.npmrc` and `vlt.json`: six files written, two backups, restore command and env hint printed | pass |
| Merged `vlt.json` keeps `config.identity` and `config.command.install`; `vlt config get registries` accepts it | pass |
| Second `apply` with the same profile is a no-op (no new backups) | pass |
| `apply` vlt-hosted with `VLT_ACCOUNT=acme`; `status` shows six files managed by vlt-hosted; a hand edit shows as `drifted` | pass |
| `restore` twice returns first to the npmjs state, then to the seeded state, byte for byte | pass |
| `--home DIR` writes under DIR and leaves HOME alone | pass |
| File snapshots after each step, diff output and status output are identical across sh, nu and ts | pass (24 comparisons) |
| Real installs of `left-pad@1.3.0` with only the user config applied: `npm`, `pnpm`, `bun`, `vlt`, `yarn` classic | all exit 0 and install 1.3.0; vlt writes `vlt-lock.json` |
| `npm config get ignore-scripts` | `true` |
| `npm config get registry`, `pnpm config get registry`, `vlt config get registries` | `https://registry.npmjs.org/` |
| Probe: profile `gate-local` (127.0.0.1:8787, nothing listening) applied; each client's install | all five fail; npm, pnpm, vlt, yarn name port 8787, bun reports `ConnectionRefused` |
| Probe: user bunfig (npmjs) plus user `.npmrc` (gate-local) | bun installs from npmjs, so bunfig wins on 1.4.2 |
| Probe: `$HOME/.bunfig.toml` (gate-local) while `XDG_CONFIG_HOME` is set | bun installs from npmjs, so that file is ignored |

During development, a fake registry on 127.0.0.1:1337 confirmed the bunfig lookup directly: bun sent its request (with the token from `$VSR_TOKEN`) when the file sat at `$XDG_CONFIG_HOME/.bunfig.toml`, or at `$HOME/.bunfig.toml` with `XDG_CONFIG_HOME` unset, and made no request to it at all when the file sat at `$HOME/.bunfig.toml` with `XDG_CONFIG_HOME` set.

## Known limits

- `apply` works file by file and is not transactional. An interrupted run leaves earlier targets applied and later ones untouched; this was observed when output was piped into `head` during development (the sh entrypoint now traps `PIPE` and `HUP` to clean its temp dir).
- `restore` works per target. If an `apply` left a target unchanged (no backup), the next `restore` rolls that target back further than the others.
- Writing by rename replaces a symlinked config file (for example one managed by a dotfiles tool) with a regular file.
- Environment variables beat every file here: `npm_config_registry`, `NPM_CONFIG_USERCONFIG`, `BUN_CONFIG_REGISTRY` and friends override what `apply` wrote. Only the userconfig case is reported.
- `vlt.json` is re-serialised with 2-space indentation; comments are not possible in it anyway, but unusual number literals may be normalised differently by jq, Nushell and JavaScript.
- The `yarnrc` (berry) target and deno were not exercised by a real client run: `not run`.
- The TypeScript entrypoint was not type-checked (`@types/bun` and `@types/node` are not installed); it runs under Bun 1.4.2.
