# 04 vlt as installer: install any repo, gate it, build selectively

Most JavaScript projects arrive with an npm, pnpm, yarn or bun lockfile and expect their own client to run every lifecycle script during install. This example uses vlt as a neutral installer for any of them. `vlt-install-any` detects what the project was built for, installs it with vlt while running no scripts at all, evaluates a gate file of `vlt query` selectors against the installed graph, and only then lets `vlt build` run the lifecycle scripts the build selector allows. Everything that happened is written to one JSON report.

Each phase is a separate process that exchanges state through JSON files, so the 07 example can wrap every phase in its own nono sandbox with only the network hosts and write paths that phase needs.

## Files

| File | Purpose |
|---|---|
| `vlt-install-any.sh`, `.nu`, `.ts` | Entrypoints with the same CLI, state files, report and exit codes |
| `gate.default.json` | Default gate rules |
| `report.schema.json` | JSON Schema 2020-12 for the report |
| `validate-report.ts` | Helper that validates reports against `report.schema.json` (implements the keywords the schema uses; no validator library is installed in the repo) |
| `fixtures/` | Small projects with lockfiles generated by the real clients (see below) |
| `test.sh` | Smoke test: every implementation against every fixture, gate block, root guard, phase interchange, layout checks, timing |

## Usage

```sh
sh  examples/04-vlt-as-installer/vlt-install-any.sh [options] <project-dir>
nu  examples/04-vlt-as-installer/vlt-install-any.nu [options] <project-dir>
bun examples/04-vlt-as-installer/vlt-install-any.ts [options] <project-dir>

# one phase at a time (what 07 wraps in nono)
sh examples/04-vlt-as-installer/vlt-install-any.sh phase <detect|fetch|gate|build|report> --state DIR [options] <project-dir>
```

| Option | Meaning |
|---|---|
| `--profile NAME` | Registry profile from `config/registry.profiles.json` (default `$VLT_LAB_PROFILE`, then `npmjs`). Its env (`VLT_REGISTRY`, `VLT_REGISTRIES`, `VLT_SCOPED_REGISTRIES`) comes from the shared renderer. |
| `--gate FILE` | Gate rules (default `gate.default.json`) |
| `--build SELECTOR` | Target for `vlt build --target` (default `:scripts:not(:built):not(:malware)`) |
| `--no-build` | Skip `vlt build`; the report lists what is pending |
| `--report FILE` | Also write the report to FILE. The report is always printed on stdout and saved as `<state>/report.json`. |
| `--keep-foreign-lockfile` | Accepted for clarity. Foreign lockfiles are always kept; vlt never reads or writes them and the report proves it with before and after checksums. |
| `--state DIR` | State directory (default: a new `mktemp` dir under `<repo>/.tmp`; required in phase mode) |
| `--pin-root` | Write an empty `vlt.json` into the project when vlt would otherwise pick a parent directory as the project root (see Known limits) |

Exit codes: `0` ok, `1` internal error, `2` usage error or refused (bad project dir, invalid gate file, root escape), `3` gate blocked (no build happened), `4` vlt install or ci failed, `5` a build failed.

## Phase contract

All phases take `--state DIR <project-dir>`. A phase reads only the state files listed as inputs and writes exactly one `<phase>.json` (plus raw logs). Any implementation can run any phase: `test.sh` runs detect in sh, fetch in nu, gate in ts, build in sh and report in nu against one state directory.

| Phase | Reads | Runs | Writes | Network | Exit |
|---|---|---|---|---|---|
| detect | project files | `vlt config location --config=project` | `detect.json` | none | 0, 2 |
| fetch | `detect.json` | `vlt install --allow-scripts=':not(*)'`, or `vlt ci --allow-scripts=':not(*)'` when `vlt-lock.json` exists | `fetch.json`, `fetch.stdout.json` (vlt's JSON), `fetch.stderr.log`; in the project `vlt-lock.json`, `node_modules/`; vlt cache | profile registry hosts | 0, 2, 4 |
| gate | `fetch.json`, gate file | `vlt query <sel> --view=json`, then `vlt query <sel> --expect-results=<expect>` per rule | `gate.json`; vlt cache (`security-archive.db`) | `api.socket.dev` for security selectors | 0, 2, 3 |
| build | `gate.json`, `fetch.json` | `vlt build --target <sel>` (skipped with `--no-build`), then `vlt query ':scripts:not(:built)'` | `build.json`, `build.stdout.json`, `build.stderr.log`; lifecycle script output in the project | whatever the allowed scripts need (esbuild 0.25.0 needs none when its platform package is installed) | 0, 3, 5 |
| report | all of the above, project lockfiles | `vlt --version` | `report.json`, stdout, `--report FILE` | none | 0 |

The build phase refuses on its own when `gate.json` is missing (`skipReason: "gate-missing"`) or blocked (`"gate-blocked"`), so a sandbox wrapper cannot skip the gate by calling build directly. The orchestrator runs detect, fetch, gate, build, report; it stops after a failed detect or fetch, always runs report, and exits with the report's `exit` (the first non-zero phase code).

### State files

- `detect.json`: `source`, `detected` (`npm`, `pnpm`, `yarn-classic`, `yarn-berry`, `bun`, `vlt`, `unknown`, or another `packageManager` name), `packageManager` (`{field, name, version}`), `lockfiles` (`[{file, kind, foreign, sha256}]`), `workspaces` (`[{source, patterns, readByVlt}]`), `npmrc` (`{present, registryLines, authLines}`), `vltRoot`, `useCi`, `warnings` (`[{code, message}]`).
- `fetch.json`: `profile`, `registry`, `command`, `mode` (`install` or `ci`), `vltExit`, `added`, `removed`, `changed`, `buildQueue` (vlt node ids), `buildQueueSource` (`vlt-output` or `query`), `pinnedRoot`, `error`.
- `gate.json`: `file`, `blocked`, `rules` (see report), `error`.
- `build.json`: `skipped`, `skipReason`, `target`, `built`, `failed`, `pending`.

Every phase file also carries `phase`, `exit` and `durationMs`.

Detection rules: the `packageManager` field wins (`yarn@1.x` is `yarn-classic`, `yarn@2+` is `yarn-berry`); otherwise the first foreign lockfile in the order `npm-shrinkwrap.json`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock` (berry when it has a top-level `__metadata:` key), `bun.lock`, `bun.lockb`; then `vlt-lock.json`. Warning codes: `foreign-lockfile-not-read`, `multiple-lockfiles`, `packagemanager-mismatch`, `pnpm-workspace-ignored`, `npmrc-ignored`, `vlt-root-escape`, `vlt-root-unknown`, and `gate-<rule>` for failing warn rules. For `.npmrc` only `registry=` and `@scope:registry=` lines are copied (URL userinfo replaced by `***`); auth lines are counted, never copied.

## Gate file format

```json
{
  "rules": [
    { "name": "malware", "selector": ":malware", "expect": "0", "severity": "block" },
    { "name": "vuln-high", "selector": ":vuln(\"<=high\")", "expect": "0", "severity": "warn" },
    { "name": "unbuilt-scripts", "selector": ":scripts:not(:built)", "expect": "0", "severity": "info" }
  ]
}
```

| Field | Meaning |
|---|---|
| `selector` | Any `vlt query` selector, evaluated in the project after fetch and before build |
| `expect` | Passed to `--expect-results` (`0`, `">0"`, `"<5"`, `">=10"`, `"<=2"`); default `"0"` |
| `severity` | `block` (a failing or erroring rule blocks the build, exit 3), `warn` (adds a `gate-<name>` warning), `info` (recorded only); default `warn` |
| `name` | Label in logs and the report; default is the selector |

Other keys (such as `note`) are ignored. Each rule ends as `pass`, `fail` or `error`. `error` means the JSON query itself failed (for example no network to `api.socket.dev`); a block rule in `error` blocks, so the gate fails closed. The default gate blocks on `:malware`, warns on `:cve`, `:vuln("<=high")`, `:obfuscated` and `:squat`, and records `:scripts:not(:built)` and `:abandoned`.

## Report

`report.schema.json` defines it. Key fields: `implementation`, `vltVersion`, `source`, `profile`, `detected`, `packageManager`, `lockfiles` (`sha256Before`, `sha256After`, `unchanged`), `foreignLockfilesUnchanged`, `vltLockfile`, `workspaces`, `npmrc`, `vltRoot`, `warnings`, `phases` (`{exit, durationMs}` per phase, `null` when a phase did not run), `fetch`, `gate.rules[]` (`name`, `selector`, `expect`, `severity`, `status`, `count`, `matches[]`, `expectExit`, `error`), `build` (`built[]`, `failed[]`, `pending[]`), `exit`. Matches are `{id, name, version}` with vlt node ids such as `~npm~esbuild@0.25.0`.

## Verified vlt 1.3.6 behaviour used here

`vlt query --view=json` returns one object per matching edge:

```json
[{
  "name": "left-pad", "fromID": "file~_d", "spec": "left-pad@1.3.0", "type": "prod", "overridden": false,
  "to": {
    "id": "~npm~left-pad@1.3.0", "name": "left-pad", "version": "1.3.0",
    "location": "./node_modules/.vlt/~npm~left-pad@1.3.0/node_modules/left-pad",
    "importer": false, "manifest": { "...": "full package.json" }, "projectRoot": "/abs/project",
    "integrity": "sha512-...", "resolved": "https://registry.npmjs.org/left-pad/-/left-pad-1.3.0.tgz",
    "dev": false, "optional": false, "confused": false, "buildState": "none",
    "insights": { "scanned": true, "malware": false, "deprecated": true, "cve": [], "vuln": {"low": false, "...": false}, "score": {"overall": 0.8, "...": 0} }
  }
}]
```

Name and version live in `to.name` and `to.version`, the stable key is `to.id`, and `to.buildState` is `none`, `needed` or `built`. A package reached through several edges appears once per edge, so the tools deduplicate by `to.id`. `to.insights` is filled once security data has been fetched.

Other observations from this machine (2026-10-04):

- `vlt install` prints `{add, added, change, changed, remove, removed, buildQueue, message}` when stdout is not a tty; `buildQueue` lists node ids such as `~npm~esbuild@0.25.0`.
- `vlt ci` prints the lockfile JSON (`{lockfileVersion, options, nodes, edges}`) instead of an install summary, so on the ci path the build queue comes from `vlt query ':scripts:not(:built)'` and `added` counts lockfile nodes.
- `vlt build` prints `{success: [{id, name, version}], failure: [], message}`.
- `vlt query <sel> --expect-results=<n> --view=json` prints nothing on stdout when the expectation fails (stderr `Error: Unexpected number of items`, exit 1). That is why each rule runs one query for details and one for the verdict.
- A project `vlt.json` containing `{"config":{"allow-scripts":"*"}}` makes a plain `vlt install` run every lifecycle script (every node ends `:built`). Passing `--allow-scripts=':not(*)'` on the command line overrides it, so fetch always passes it.
- `:vuln("<cmp><level>")` compares the numeric level index (critical=0, high=1, medium=2, low=3). esbuild 0.25.0 has only a low advisory, yet `:vuln(">=high")` and `:vuln(">=critical")` match it, while `:vuln("<=high")` and `:vuln(high)` do not. Use `"<=high"` for "high or critical".
- vlt picks its project root by walking up from the working directory to `$HOME` (exclusive): the first `vlt.json` wins, otherwise the topmost directory with a `package.json` or `node_modules`, stopping at a directory that contains `.git` (`find` in the bundled config module). A project copied below the vlt-lab checkout therefore resolves to the repository root, and a project below any other `package.json` installs into the parent. Detect records this as `vltRoot`; fetch refuses with exit 2 unless `--pin-root` writes an empty `vlt.json` into the project.

## Known limits

- **Fresh resolution.** vlt reads none of `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock` or `bun.lockb`. Versions come from the `package.json` ranges at install time and can differ from what the project's lockfile pinned. The fixtures use exact versions, so the installed set matches here; a project with `^` ranges may get newer versions.
- **pnpm workspaces.** `pnpm-workspace.yaml` is not read, so its workspace packages are not linked or installed. Root dependencies that use `workspace:` specs will fail to resolve. Move the globs to `vlt.json` `"workspaces"` (detect lists them).
- **`.npmrc` is ignored.** Registries and scopes come only from the vlt-lab profile env. Private scopes configured in `.npmrc` fail to resolve unless the profile routes them (`VLT_SCOPED_REGISTRIES`). Auth must be provided as `VLT_TOKEN` or per-registry `VLT_TOKEN_<url>` variables.
- **node_modules layout.** Packages live in `node_modules/.vlt/<id>/node_modules/<name>` with top-level symlinks. Node resolution and `npm ls` worked in this test; tools that walk `node_modules` without following symlinks, expect hoisted transitive dependencies at the top level, or patch files in place (patch-package style) may break.
- **Project root walk-up.** vlt can choose a parent directory as the project root (see above). The tool refuses by default; `--pin-root` adds an empty `vlt.json` to the project, which is one more file in the user's tree.
- **Gate needs network.** Security selectors call `api.socket.dev`. Without it a block rule becomes `error` and the gate blocks. Security data only exists for packages from the registry configured as `registries.npm` or registry.npmjs.org.
- **Two queries per rule.** `--expect-results` hides the JSON on mismatch, so each rule costs two `vlt query` calls (cached after the first).
- **`vlt ci` output.** On projects that already have `vlt-lock.json`, `fetch.added` is the number of lockfile nodes and `removed`/`changed` are null.
- **Build failures** are reported from vlt's `failure` array; its item shape was not observed (no failing build was produced in testing), so non-object items are recorded as `{id: <string>, name: null, version: null}`.
- **shellcheck** is not installed here; the sh files pass `dash -n` only.
